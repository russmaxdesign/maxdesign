Understanding aria-level

Published: 17 August 2026

What is the aria-level attribute?

aria-level tells assistive technology where an item sits in a hierarchy.

The value must be a whole number starting at 1. An item at the first level uses 1, an item nested under it uses 2, and an item nested under that uses 3.

The value has no upper limit in the spec, so it doesn't stop at 6 like native heading levels do. More on what that means in practice under "Is there really no limit?" below.

aria-level can be used on items that have levels, such as tree items, elements with role="heading", and rows in a treegrid.

Where it can be used

  • Elements with role="heading", where aria-level is used to set the heading level.
  • Rows inside a treegrid, where aria-level can identify the level of each row.
  • Tree items, where aria-level can identify their level within the tree.
  • Some newer or less common roles, such as comment and associationlistitemkey.

Where it shouldn't be used

  • Native heading elements such as <h1> to <h6> don't need it, their level is already set by the element name.
  • On roles that don't support aria-level, such as listitem or option.
  • Where the structure already makes the level clear, such as properly nested tree items.
  • As a substitute for creating the correct hierarchy. aria-level tells assistive technology the level of an item; it doesn't create the relationships between items.

Let's look at three uses for aria-level.

Example 1: creating a heading

Imagine content is being added to a page from a CMS field, a syndicated feed or an API response.

The content is a title string with no indication of what heading level it should use. In cases like this, heading structure could be added with role="heading" and aria-level.

<div role="heading" aria-level="2">
  This behaves like a heading, level 2
</div>

Example 2: headings inside cards

Imagine a related content card that gets its title from a CMS or API. The title is just a string, with no heading level attached to it.

The same card could be used in different parts of a page. In one place, its title might need to be a level 2 heading. In another, it might need to be level 3.

Because the card doesn't know where it will appear on the page, it may not know which heading level to use.

In cases like this, the heading level can be set when the card is added to the page.

In the first example, the card heading is set to level 2:

<div class="card">
  <div role="heading" aria-level="2">
    Related article
  </div>
</div>

The same card could then use a different level in another part of the page. In this case, level 3.

<div class="card">
  <div role="heading" aria-level="3">
    Related article
  </div>
</div>

This means that the same card component can use a heading level that fits its position on the page.

Example 3: aria-level in a treegrid (try it on the test page)

aria-level can also be used on rows inside a treegrid.

A treegrid can show "hierarchical data" in rows and columns. The rows may sit one-after-another in the DOM, even when some rows are visually nested inside others.

In this case, aria-level tells assistive technology the level of each row.

For example, in a file browser:

  • "Reports" could be at level 1.
  • a folder inside "Reports", like "Archive", could be at level 2.
  • a file inside that folder, like "Q1 report.docx" could be at level 3.

The hierarchy comes from the aria-level value on each row rather than from nested HTML.

<div role="row" aria-level="1" aria-expanded="true">
  <span role="gridcell">Reports</span>
</div>

<div role="row" aria-level="2" aria-expanded="true">
  <span role="gridcell">Archive</span>
</div> 

<div role="row" aria-level="3">
  <span role="gridcell">Q1 report.docx</span>
</div>

A native table is usually the better choice for flat data. But a treegrid is useful when the data has a hierarchy, multiple columns and interactive keyboard navigation between cells.

A treegrid can use whatever level the hierarchy needs, there's more on limits and support just below.

Is there really no limit?

The spec places no upper limit on aria-level, so it doesn't stop at 6 like native heading levels do. In practice, though, support for heading levels above 6 is inconsistent: the ARIA 1.3 draft notes that values above 6 can cause difficulties for users, Windows' UI Automation accessibility API caps heading levels at 9, and Chromium enforces this by falling back to 6 for anything higher.1 This constraint is documented for headings specifically, whether it also applies to aria-level on treegrid rows is untested.

Takeaway

aria-level can be used to provide hierarchy when semantic markup and structure are not available.
