Is aria-label allowed on static elements?

Published: 03 January 2026

There is a commonly held belief that the aria-label attribute “cannot” be used on static (or non-interactive) elements.

While the ARIA and HTML specifications do not forbid aria-label purely on the basis of an element being ‘static’, they do prohibit its use when an element’s implicit or explicit role does not support ‘name from author’ (see ARIA in HTML, section 5.2.8).

The simplest way to think about it:

aria-label is intended for elements whose roles support author-provided accessible names. These roles can be either implicit (native to the HTML element) or explicit (assigned via ARIA).

Note that "static" (meaning non-interactive) is not a term the specs use; the actual criterion is always about the role, not interactivity.

As you will see below, there are legitimate cases where static elements use aria-label, either because they have a native role or because an appropriate ARIA role is applied.

In this article, we examine how aria-label behaves on static elements in practice, across browsers and platforms, and why real-world behaviour is often more nuanced than common assumptions suggest.

The examples include clearly flagged bad-practice patterns alongside legitimate use cases, to show what is exposed at the accessibility API level — and why exposure alone does not imply recommendation.

Different ways aria-label could be used

Let’s look at some methods that could be used to apply the aria-label to elements, and how they are rendered in different browsers' accessibility trees.

Notes:

  1. Some of the examples below intentionally demonstrate poor or incomplete accessibility patterns. They are included only to test whether an accessible name is exposed, not to endorse their use in real-world interfaces.
  2. Several of the examples shown here are also flagged as invalid HTML. This further reinforces why these patterns should not be used in production, even if an accessible name appears to be exposed.
  3. These results show exposure at the accessibility API level. Actual announcement and user experience may vary by assistive technology.
  4. “Pass” indicates that a name is exposed in the accessibility tree for the purposes of testing. It does not imply that the pattern is recommended or appropriate for production use.

Group 1. Interactive elements with aria-label (control group)

1.1 No visible label - such as an icon inside a button

<button aria-label="Dismiss">
  <img src="icon-cross.png" alt="">
</button>

This method is acceptable if there is no visible text label available. For example, the button inludes an icon only.

Pass criteria: The <button> has a name of "Dismiss" that is presented in the accessibility tree.

Group 4. Static elements with aria-label inside interactive elements (bad practice)

This pattern often appears when icon libraries are used. Developers may apply the accessible name to the icon element itself rather than the interactive control.

<button>
  <i class="fa fa-close" aria-label="Close"></i>
</button>

Font Awesome does not recommend applying accessible names to the <i> element itself. This example reflects a common developer mistake, not recommended usage.

While this method provides an accessible name for the button via name-from-content, a more robust solution would be to add the aria-label directly to the <button> element.

This pattern is also invalid HTML. For <i> elements, aria-label must not be used if there is no ARIA role present. It also must not be used when the element has any of the following roles: caption, code, deletion, emphasis, generic, insertion, paragraph, presentation, strong, subscript, or superscript.

Pass criteria: The <button> has a name "Close" that is presented in the accessibility tree.

6.2 Element using aria-hidden

<i  class="fa fa-delete" aria-hidden="true" aria-label="Delete">
</i>

This pattern also appears in icon-library usage. Developers may correctly hide the icon from assistive technologies using aria-hidden="true", but then mistakenly add an aria-label, assuming it will still be announced to assistive technologies.

Because the element is explicitly hidden from the accessibility tree, the accessible name is never exposed. This pattern does not provide an accessible name and should be avoided.

This pattern is also invalid HTML. For <i> elements, aria-label must not be used if there is no ARIA role present. It also must not be used when the element has any of the following roles: caption, code, deletion, emphasis, generic, insertion, paragraph, presentation, strong, subscript, or superscript.

Pass criteria: The element should have no name in the accessibility tree.

Conclusion

At the start of this article, we noted that neither the ARIA nor HTML specifications explicitly forbid the use of aria-label on static elements.

The tests above help explain why this belief exists. In practice, modern browsers and assistive technologies often do surface accessible names from static elements, even if they have no explicit role.

However, the fact that these patterns may appear to work does not mean they are robust, future-proof, or produce valid markup. Some of the demonstrated patterns rely on browser heuristics, may behave inconsistently across platforms or assistive technologies, and in several cases are also invalid HTML.

For these reasons, when an accessible name is critical to understanding or operating an interface, you should first aim to use native text or native semantic mechanisms.

If this is not possible, the name should be applied directly to a name-bearing element using well-supported, valid patterns.
