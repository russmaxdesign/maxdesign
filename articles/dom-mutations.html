What are DOM mutations?

Published: 5 December 2025

The DOM is a tree-like structure that shows all the elements in your HTML document.

It is "live", which means it reacts to changes. It is not a passive version of your HTML.

"DOM mutations" are changes to this tree. There are three types:

  • Nodes being added or removed — e.g. a new element being inserted.
  • Attributes changing — e.g. an open attribute being added or removed.
  • Text changing — e.g. the text inside an element being replaced.

These mutations can happen with or without JavaScript.

DOM mutations without JavaScript

Browsers make some DOM mutations on their own. For example:

  • internal UI logic — e.g. the browser adding or removing the open attribute on a <details> element when the <summary> is clicked.
  • dialog behaviour — e.g. the browser removing the open attribute from a modal <dialog> when the user presses Esc.
  • parsing — e.g. the browser inserting nodes as it builds the page, including adding missing elements or restructuring malformed HTML.

None of these modifications need to be made using JavaScript. Some HTML elements have built-in behaviours, and browsers update the DOM to keep things "in sync".

State changes are not DOM mutations

Many things that feel like DOM changes are actually state changes. The browser tracks these internally, as properties or states, but the DOM tree itself does not change.

Common examples include:

  • user input — e.g. typing into an <input> updates its value property, not its value attribute.
  • checkboxes and radio buttons — e.g. checking a checkbox updates its checked property, not its checked attribute.
  • select menus — e.g. choosing an option in a <select> updates which option is selected, but does not add a selected attribute.
  • validation results — e.g. a form control matching :invalid because of built-in browser validation.
  • autofill — e.g. the browser writing values into <input> fields.
  • focus — e.g. an element receiving keyboard focus.

This difference matters when debugging, as you will see in the MutationObserver section below. But from an accessibility point of view, state changes are just as important as DOM mutations. Both are used to update the accessibility tree.

JavaScript and the DOM

JavaScript can also be used for DOM mutations.

When your script runs, it can directly change the structure, text, or attributes of elements. Every one of these changes counts as a DOM mutation.

Typical JavaScript-driven mutations include:

  • Adding nodes — inserting new elements into the DOM, such as adding an error message or appending a list item.
  • Removing nodes — deleting elements from the DOM, such as removing a modal, clearing a list, or hiding elements by removing them entirely.
  • Updating attributes (including ARIA) — changing values like aria-expanded, class, or disabled. Every attribute update counts as a DOM mutation.
  • Changing text — modifying the textContent or innerText of an element, such as updating live status messages or replacing placeholder content.

JavaScript can also change state, and this is where things get a little tricky. Some properties are linked to an attribute, and some are not:

  • Setting details.open = true also adds the open attribute. This is a DOM mutation.
  • Setting input.value = "hello" only changes the property. The value attribute stays the same, so this is a state change, not a DOM mutation.

These are sometimes called “JavaScript-driven DOM mutations” or “JS mutations”, but they are not really a special category. They are just another way the DOM changes.

Watching DOM mutations with MutationObserver

Browsers have a built-in API called MutationObserver that lets you watch DOM mutations as they happen. This can be a handy debugging tool when you want to see exactly what is changing.

Paste this into your browser's console:

const observer = new MutationObserver((mutations) => {
  mutations.forEach((m) => {
    console.log(m.type, m.target, m.attributeName || '', m.oldValue || '');
  });
});

observer.observe(document.body, {
  subtree: true,
  childList: true,
  attributes: true,
  attributeOldValue: true,
  characterData: true
});

Now try these:

  1. Open a <details> element. You will see an attributes mutation for the open attribute.
  2. Type into an <input>. Nothing is logged.
  3. Check a checkbox. Nothing is logged.

Why? Typing changes the input's value property, and checking a checkbox changes its checked property. Neither changes an attribute, so the DOM tree itself has not changed. These are state changes, not DOM mutations. The browser still updates the AXTree, though, so screen readers can announce the new value or state.

To stop watching, run observer.disconnect().

If you prefer not to use code, most browser DevTools let you right-click an element in the Elements panel and choose "Break on" attribute or subtree modifications.

Why DOM mutations matter for accessibility

When the DOM mutates, or when an element's state changes, browsers need to update the accessibility tree (AXTree). Screen readers and other assistive technologies use this tree.

Whenever one of these changes happens:

  • The browser updates the AXTree.
  • It compares the old and new tree.
  • It fires AXEvents 1 for anything meaningful that changed such as:
    • Name changes
    • Value changes
    • Expanded/collapsed state
    • Focus changes
    • Role changes
    • Live region updates

These AXEvents then travel through the operating system’s accessibility API to the screen reader, which interprets them and decides whether, when, and how to announce the change.

Not all AXEvents result in announcements. Screen readers may merge, delay, or ignore certain events based on their behaviour and user settings.

If we return to the examples above, we can see that DOM mutations and state changes both push information into the AXTree:

  • The <input> value (a state change) is exposed as the control’s value.
  • The <select> option (a state change) is exposed as the element’s accessible value.
  • The <details> open/closed state (a DOM mutation) is mapped to accessibility state.

These updates happen because the browser does not keep a separate copy of your original HTML. Instead, it continuously updates accessibility information from the live, constantly changing DOM and the state of each element.

Why this matters

DOM mutations and state changes have a direct influence over:

  • What screen readers announce.
  • How quickly these announcements occur.
  • Which events interrupt others.
  • Whether changes are even detectable.

Every meaningful DOM mutation or state change means that browsers have to update accessibility information and fire accessibility events.

Wrapping up

  • The DOM is not static.
  • DOM mutations are changes to nodes, attributes, or text.
  • The browser performs some DOM mutations on its own, even without JavaScript.
  • JavaScript can also create DOM mutations.
  • Many changes, like typing or checking a checkbox, are state changes rather than DOM mutations.
  • You can use MutationObserver to see which changes are DOM mutations.
  • Both DOM mutations and state changes flow into the AXTree, and shape accessibility updates, announcements, and timing.
