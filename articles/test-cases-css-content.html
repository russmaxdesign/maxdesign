Tests for CSS generated content alternative text

Published: 28 December 2025

Sometimes, designers use CSS content: to add text or icons before or after elements. If that content is meant to be seen, it might also need an accessible version for people who can’t see it.

The spec allows you to add alternative text by putting it after a slash in the content property. For example:

.icon::before {
  content: "🔍" / "Search";
}

The part before the slash is what’s shown visually - in this case, a magnifying glass icon.

The part after the slash is intended to act as alternative text - in this case “Search”.

In supporting browsers, this alternative text may be exposed to the accessibility tree and could be used by assistive technologies in place of the visible CSS content.

As you can see in the test results below, support is inconsistent across browsers and screen readers. There is no guarantee this text will participate in accessible name computation or be announced by a screen reader, even when it appears in the accessibility tree.

Test criteria:

  1. Is the generated content announced for assistive technologies when the element receives focus?
  2. Is the generated content alternative text announced for assistive technologies when the element receives focus?

For these tests, “announced” means that the exact string (for example, “Visible generated content” or “Hello world”) is spoken when the block receives keyboard focus (such as via the TAB key). Partial or generic announcements like “and one other item” are treated as failures.

Notes

  • Each block is tabindex="0" for easy focus testing.
  • Generated text is from ::after pseudo-elements.
  • The part after / is the alternative text for assistive technologies.

Test cases

Example 1:

This is example 1 
.test-old::after {
  content: "Visible generated content";
}

Pass should be:

  1. "Visible generated content" should be announced.
  2. There is no test for alternative text as it is not present.

Example 2:

This is example 2 
.test-alt-only::after {
  content: "" / "Hello world";
}

Pass should be:

  1. Generated content should not be announced (left blank).
  2. "Hello world" alternative text should be announced.

Example 3:

This is example 3 
.test-visible-only::after {
  content: "Visible generated content" / "";
}

Pass should be:

  1. "Visible generated content" should be announced.
  2. Alternative text should not be announced (left blank).

Example 4:

This is example 4 
.test-both::after {
  content: "Visible generated content" / "Hello world";
}

Pass should be:

  1. "Visible generated content" should be announced.
  2. "Hello world" alternative text should be announced.

Summary of findings

In the engines tested, CSS-generated alternative text often appears too late in the rendering and accessibility pipelines to reliably participate in accessible name computation. In many cases, announcements depend on assistive technology heuristics rather than a predictable browser implementation.

Based on these results, the CSS content alternative text syntax is not reliable enough to be used as a primary accessibility mechanism.

  • Support is highly inconsistent. No browser and screen reader combination passed all tests. Even the most successful stacks produced a mix of passes and fails across the four examples.
  • Presence in the accessibility tree does not guarantee speech. In several cases (for example, macOS Firefox and Safari with VoiceOver), generated content and alternative text were exposed to the accessibility tree, but VoiceOver announced only a generic message such as “and one other item” instead of the actual text.
  • Alt-only content is the least-bad pattern, but still fragile. Example 2 (no visible text, alt text only) worked in some browser and screen reader combinations, but failed in others. It cannot be relied on for critical information.
  • Visible + alt together is the most fragile. Example 4 (visible text and alternative text) almost never produced both expected announcements. In many cases only one string, or neither, was spoken.
  • Some stacks fail completely. macOS Safari with VoiceOver did not announce generated content or alternative text in any test.
  • Recommendation. Treat this syntax as experimental. For important information, continue to use semantic HTML and ARIA. Do not rely on CSS-generated content as the sole mechanism for accessibility.

Disclaimer

Test results involving operating systems, browsers, and assistive technologies must be interpreted with care. There are many moving parts — OS versions, browser engines, assistive technology configuration, and even AT verbosity settings — which makes exact replication extremely difficult. These results reflect the versions and conditions listed, with screen readers kept as close to default “manufacturer settings” as possible to support reasonable reproducibility.

Despite these variables, the consistency of failures across multiple stacks provides meaningful evidence that this feature should be treated as experimental until interoperability improves.
