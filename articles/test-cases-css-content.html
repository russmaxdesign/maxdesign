Tests for CSS generated content alternative text

Published: 27 December 2025

Content intended for visual media sometimes needs alternative text for speech output or other non-visual mediums. The content property accepts alternative text to be specified after a slash (/) after the last <content-list>. If such alternative text is provided, it must be used for speech output instead.

Source

This alternative text is presented as a new node in the accessibility tree, for browsers that support it.

Test criteria:

  1. Is the generated content announced for assistive technologies when the element receives focus?
  2. Is the generated content alternative text announced for assistive technologies when the element receives focus?

For these tests, “announced” means that the exact string (for example, “Visible generated content” or “Hello world”) is spoken when the block receives keyboard focus (such as via the TAB key). Partial or generic announcements like “and one other item” are treated as failures.

Notes

  • Each block is tabindex="0" for easy focus testing.
  • Generated text is from ::after pseudo-elements.
  • The part after / is the alternative text for assistive technologies.

Test cases

Example 1:

This is example 1 
.test-old::after {
  content: "Visible generated content";
}

Pass should be:

  1. "Visible generated content" should be announced.
  2. Alternative text should not be announced (not present).

Example 2:

This is example 2 
.test-alt-only::after {
  content: "" / "Hello world";
}

Pass should be:

  1. Generated content should not be announced (left blank).
  2. "Hello world" alternative text should be announced.

Example 3:

This is example 3 
.test-visible-only::after {
  content: "Visible generated content" / "";
}

Pass should be:

  1. "Visible generated content" should be announced.
  2. Alternative text should not be announced (left blank).

Example 4:

This is example 4 
.test-both::after {
  content: "Visible generated content" / "Hello world";
}

Pass should be:

  1. "Visible generated content" should be announced.
  2. "Hello world" alternative text should be announced.

Summary of findings

In the engines tested, CSS-generated alt text appears to be computed too late in the rendering pipeline to consistently participate in accessible name computation. As a result, announcements often depend on AT heuristics rather than reliable browser behaviour.

With that in mind, these tests show that the CSS content alternative text syntax is not reliable enough to be used as a primary accessibility mechanism.

  • Support is highly inconsistent. No browser and screen reader combination passed all tests. Even the best stacks had a mix of passes and fails across the four examples.
  • Being in the accessibility tree does not guarantee speech. In several cases (for example, macOS Firefox and Safari with VoiceOver), generated content and alternative text appear as nodes in the accessibility tree, but VoiceOver announces only a generic message such as “and one other item” instead of the actual text.
  • Alt-only content is the least-bad pattern, but still fragile. Example 2 (no visible text, alt text only) worked in some browser and screen reader combinations, but still failed in others, so it cannot be relied on for critical information.
  • Visible + alt together is the most fragile. Example 4 (both visible text and alternative text) almost never produced both expected announcements. Often only one string, or neither, was spoken.
  • Some stacks fail completely. macOS Safari with VoiceOver failed all tests: neither generated content nor alternative text was announced for any example.
  • Recommendation. At this time, the CSS generated content alternative text syntax should be treated as experimental only. For important information, continue to use semantic HTML and ARIA, rather than relying on CSS-generated content for accessibility.

Disclaimer

Any test results involving operating systems, browsers, and assistive technologies must be interpreted with care. There are many moving parts at play — OS versions, browser engines, assistive technology configuration, and even individual AT verbosity settings — which makes exact replication extremely difficult. My results reflect the versions and conditions listed, with screen readers kept as close to default “manufacturer settings” as possible to ensure that another tester could reasonably reproduce the behaviour observed here.

Even with these variables, the consistency of the failures observed across multiple stacks provides meaningful evidence that this feature should continue to be treated as experimental until interoperability improves.
