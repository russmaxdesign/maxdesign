Did you know the true power of some ARIA roles?

A single sentence hidden in an obscure spec

A lot of people do not realise that some ARIA roles can erase existing semantics entirely.

This behaviour is stated clearly in only one place, buried inside the Core Accessibility API Mappings 1.2 specification:

If the host language element is overridden by a WAI-ARIA role whose semantics or structure is not equivalent to the native host language semantics or to a subclass of those semantics, then treat any child elements having roles specified as Allowed Accessibility Child Roles as having presentation or none.

[] ------------------ ## 2. The same statement in plain language Here is the same rule from the specification, rewritten in plain language: When you apply certain ARIA roles, the browser stops using the element’s native structure. From that point on, only child elements that explicitly match the ARIA role’s expected structure remain accessible. Any other child elements are treated as presentation only. This is not additive behaviour. In these cases, ARIA does not “enhance” existing semantics. It replaces the entire semantic model of the element, including how its children are interpreted. Once this happens, the browser no longer assumes anything about native HTML relationships. Every meaningful part of the widget must be stated explicitly using ARIA roles. ------------------ ## 3. The same structural replacement happens with many widget roles. Here are some other examples: - menu → menuitem, menuitemcheckbox, menuitemradio - tablist → tab - listbox → option - tree → treeitem - grid → row → gridcell - menubar → menuitem In all of these cases, native HTML semantics are ignored once the ARIA widget role is applied. ------------------ ## 6. When this rule does not apply So far, this article has shown how some ARIA roles replace the entire semantic structure of an element and wipe native child semantics. However, there is an important exception. The specification includes a qualifying phrase that is easy to miss: | “…whose semantics or structure is not equivalent to the native host language semantics…” Those few words carry a lot of weight. They define when ARIA replaces semantics and when it merely reinforces them. ### Two rules to understand Once this is unpacked, the behaviour becomes more predictable. Rule 1 Some ARIA roles replace the entire semantic model of an element, including how its children are interpreted. Rule 2 That replacement only happens when the ARIA role’s semantics are not equivalent to the native HTML model. When the ARIA role introduces a different widget model, native structure is discarded and must be rebuilt explicitly using ARIA roles. When the ARIA role matches an existing native model, the browser keeps the native semantics. An example where semantics are preserved Consider the following markup:

    Do you like boats?

    In this case: - Native radio inputs already expose role="radio". - The grouping behaviour already exists in HTML. - The ARIA radiogroup role matches the native semantic model. Because the semantics are equivalent, the browser does not discard the child roles. The radio buttons remain intact and correctly exposed to assistive technologies. Here, ARIA is reinforcing an existing model rather than replacing it. ### Why this distinction matters Without this context, ARIA can feel inconsistent. Sometimes applying a role appears to wipe child semantics. Other times it does not. The difference is not arbitrary. It depends on whether the ARIA role introduces a new widget model or aligns with an existing native one. Once you recognise this distinction, a lot of previously confusing ARIA behaviour starts to make sense. ------------------ 7. Conclusion ARIA is not just a set of attributes. Some roles opt you into an entirely new semantic system. When that happens, native structure stops mattering unless you rebuild it explicitly. Understanding which ARIA roles replace structure, and which merely reinforce it, explains a huge amount of “mysterious” accessibility breakage.
