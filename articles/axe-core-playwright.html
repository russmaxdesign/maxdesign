axe-core, Playwright and Cucumber: accessibility testing in the development lifecycle

Published: 9 October 2026 | Author: Russ Weakley

If you work in accessibility, you have probably heard of automated testing tools such as axe.

But developers and engineers often approach accessibility testing differently. They can building accessibility checks into the development process, so issues can be caught before they reach the finished product.

This is where tools such as axe-core, Playwright and Cucumber can fit.

  • axe-core finds automatically detectable accessibility problems
  • Playwright controls a real browser, and can test how the website behaves, including its accessibility
  • Cucumber describes expected behaviour in a readable format

They can be used independently, but they become especially useful when combined.

One thing worth knowing up front: Playwright can do accessibility testing on its own, without axe-core. We'll see how shortly.

axe-core

axe-core is an accessibility testing engine.

If you have used the axe DevTools browser extension, you have already used axe-core. It is the engine inside that extension, and inside many other accessibility tools.

axe-core runs inside the web page itself. You load a page, run axe-core against it, and it checks the rendered page for automatically detectable accessibility problems.

These can include things such as:

  • missing accessible names
  • invalid ARIA
  • colour contrast
  • form labelling
  • landmark issues
  • heading-related issues
  • structural accessibility problems

At its simplest:

Page loads
↓
axe-core runs inside the page
↓
axe-core returns its results

Each problem axe-core finds is given an impact level: minor, moderate, serious or critical. This helps teams decide what to fix first.

Where axe-core really shines is breadth: it can sweep a whole page for a wide range of common problems in one go, without anyone needing to write a test for each one.

axe-core is also honest about what it doesn't know. Alongside its violations, it returns "incomplete" results: things it couldn't decide automatically and that need a person to check. A common example is colour contrast for text over a background image or gradient.

That points to the important limitation: axe-core can only detect issues that can be determined automatically.

It cannot reliably answer questions such as:

  • Is the focus order logical?
  • Is a visible label meaningful?
  • Does the alt text appropriately describe the image?
  • Is the experience understandable with a screen reader?
  • Is the keyboard interaction appropriate for this component?

So axe-core provides automated accessibility testing, not a complete accessibility audit.

Playwright

Playwright is a browser automation and testing framework.

It can control a browser much like a person would interact with a website.

For example, Playwright can:

  • open a page
  • log in
  • click buttons
  • complete forms
  • open dialogs
  • navigate between pages
  • use keyboard commands
  • wait for dynamic content
  • inspect elements and states
  • take screenshots

This means Playwright can get an application into the exact state you want to test.

For example:

Open checkout page
↓
Add a product to the cart
↓
Open the cart dialog
↓
Run an accessibility test

This is one place where Playwright and axe-core fit together well. axe-core can inspect the current page, but it does not navigate through the application itself. Playwright can do that navigation, then run axe-core inside the page it has opened. There is even an official package, @axe-core/playwright, that connects the two.

But Playwright is much more than a way to get pages ready for axe-core.

Playwright can test accessibility on its own

Playwright can work with accessibility information such as roles, accessible names and descriptions, much like the information exposed to assistive technologies.

For example, Playwright can find elements by their role and accessible name:

page.getByRole('button', { name: 'Submit' })

If the button does not expose the expected accessible name, that locator will not match it and the test fails. Just finding elements this way is already a small accessibility check.

axe-core would also flag a button with no accessible name at all. But only a test like this can confirm the name is the right one.

Playwright also has checks (called assertions) built specifically around accessibility, such as:

  • toHaveAccessibleName: does this element have the expected accessible name?
  • toHaveAccessibleDescription: does it have the expected accessible description?
  • toHaveRole: does it have the expected role?
  • toHaveAccessibleErrorMessage: is the expected error message connected to it?
  • toBeFocused: does this element currently have keyboard focus?

It can also take an ARIA snapshot, a simple text outline of how part of the page appears in the accessibility tree, and compare it against what you expect.

Here is a complete accessibility test with no axe-core in it at all:

test('Escape closes the dialog and returns focus', async ({ page }) => {
  const trigger = page.getByRole('button', { name: 'Open settings' });
  await trigger.click();
  await expect(page.getByRole('dialog')).toBeVisible();

  await page.keyboard.press('Escape');

  await expect(page.getByRole('dialog')).toBeHidden();
  await expect(trigger).toBeFocused();
});

Even if you don't write code, you can probably read what this does: open the dialog, press Escape, check the dialog has closed, and check focus went back to the button that opened it.

That is functional accessibility testing: checking that things actually behave accessibly, not just that the code looks right to an automated scanner.

Cucumber

Cucumber sits at a different level.

Rather than controlling the browser or checking accessibility rules, Cucumber lets you describe expected behaviour in plain language, then runs those descriptions as tests.

It uses a language called Gherkin.

For example:

Feature: Checkout accessibility

Scenario: Checkout form has no automatically detectable accessibility issues
  Given I am on the checkout page
  When I run an accessibility scan
  Then there should be no serious or critical accessibility violations

Each of those plain-language lines is connected to a small piece of test code called a step definition.

For example:

Given I am on the checkout page
→ Playwright opens the page

When I run an accessibility scan
→ axe-core runs

Then there should be no serious or critical accessibility violations
→ the test checks the axe-core results

Cucumber therefore does not perform the accessibility testing itself.

Instead, it provides a readable behavioural layer around the tests.

This can be useful when developers, testers, accessibility specialists and product teams need a shared understanding of what behaviour is expected.

A small practical note: Playwright comes with its own test runner, and so does Cucumber. When teams use both tools, Cucumber usually runs the tests and calls on Playwright to control the browser. You don't use both runners at once.

Gherkin and accessibility acceptance criteria

One interesting thing about Gherkin is how naturally it can express accessibility requirements.

Its basic structure is:

Given ...
When ...
Then ...

For example:

Scenario: Closing a dialog with Escape
  Given the dialog is open
  When I press the Escape key
  Then the dialog should close
  And focus should return to the button that opened it

Look familiar? It's the same behaviour as the Playwright test above, just written for people instead of computers.

This is essentially structured acceptance criteria.

Instead of saying:

The dialog must be accessible.

we are describing a specific behaviour that can actually be tested.

That makes Gherkin particularly interesting for accessibility requirements involving things such as:

  • keyboard interaction
  • focus management
  • form errors
  • dialogs
  • menus
  • dynamic content
  • state changes

How they fit together

The three tools operate at different layers.

A useful mental model is:

Cucumber / Gherkin
"What behaviour are we testing?"
        ↓
Playwright
"Interact with the application and test the expected behaviour."
        ↓
Optional: axe-core (runs inside the page Playwright has opened)
"Check this state for automatically detectable accessibility problems."

Consider a registration form.

You might describe the requirement using Gherkin:

Scenario: Email validation error

  Given I am on the registration form
  When I submit the form without entering an email address
  Then the email field should have an accessible error message

Playwright could then:

Open the registration page
↓
Submit the form
↓
Find the email field
↓
Check the error message appears
↓
Check the error is connected to the field
↓
Check where focus moved

axe-core could then scan the resulting page for automatically detectable accessibility problems.

But notice that axe-core couldn't do the earlier step for us. It cannot reliably infer which text on the page is intended to be the field's error message if that relationship is missing. Playwright can check this directly, using toHaveAccessibleErrorMessage or toHaveAccessibleDescription (depending on how the error is connected).

The simplest mental model

If you only remember one thing:

  • axe-core: Scans a page for automatically detectable accessibility problems
  • Playwright: Drives the website and tests how it behaves, including accessibility behaviour
  • Cucumber: Runs expected behaviour written as readable scenarios
  • Gherkin: The structured language used to write those scenarios

Playwright can test accessibility behaviour on its own. axe-core adds a broad automated scan on top. Many teams use both.

Cucumber is optional. It becomes particularly useful when you want accessibility requirements expressed as reusable, human-readable acceptance criteria rather than only as developer test code.

Together, these tools can help move accessibility testing earlier into development, while also expanding testing well beyond a simple automated scan.

And none of them replace testing with real people, including people who use assistive technologies every day.
